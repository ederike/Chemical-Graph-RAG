## 四、当前构建方案

知识库构建由 `main.py` 驱动，阶段顺序为 **接入 → 识别入库 → 摘要 → 分块 → 实体抽取 → 超图构建 → 向量化**，并以 SQLite 行级 `status` 作为断点：上一阶段写完的状态，就是下一阶段的待处理集合。源文件来自对象存储批量拉取或本地 `doc/`。各阶段具体如下。

**1. 文档接入与去重**

从业务库读取产品附件元数据，按 OSS 对象键下载到工作目录。下载侧以 `oss_url` 去重，避免同一对象反复拉取；本地再按文件内容 MD5 折叠字节级重复件，优先保留哈希文件名。该步骤只落盘，不识别、不入库。

**2. PDF 识别入库**

将 PDF 按页渲染为 JPEG（dpi=100），交给视觉语言模型 `qwen3.6-27b` 做版面转写，得到纯文本 `doc.content`。单份 PDF 超过 `max_pages_per_doc=4` 时，按页窗切成多条独立 `doc` 记录（流水线标识 `page_slice_plain_text_v1`）：首段沿用原文件名，后续为 `{文件名}_{n}`。`extra` 中保留源文件、页范围、切片序号与切片总数，供后段摘要衔接与检索时判断是否扩全文。识别结果按批 flush（默认 500 条）写入 `doc` 表，并统计 token。已存在的切片名默认跳过，便于断点续跑。

**3. 文档摘要（summary）**

对每条已入库文档的全文调用 `qwen3.6-27b` 生成摘要，写入该文档唯一超边 `hyperedge.content`（一篇文档对应一条超边）。长 PDF 的后段切片会注入同文件前序切片的识别正文作为先验，提示词要求结合前文、但重点覆盖本段，减轻切片切断导致的指代缺失。16 线程并发，开启生成缓存；完成后文档状态进入待分块。

**4. 语义分块（chunk）**

只处理已完成摘要的文档。每篇切出两类块：头块 `head` 直接取超边摘要、不再二次切分；正文块 `body_1…` 在句边界上按 token 打包，块长上限 512，相邻块保留 10% 重叠，避免指标、牌号被从中间切断。块写入 `chunk` 表，初始 `status=new`，文档状态改为 `chunk`；头块 id 回写到对应超边的 `chunk_id`。缓冲区约 1000 条落盘一次。分块只做切分与持久化，不做模型调用。

**5. 实体抽取（extract）**

扫描 `status=new` 的块，用 `qwen3.6-27b` 按 JSON 协议抽出「实体名 → 描述」字典（兼容多种返回形态，只保留合法 entities）。结果写入该块 `extra.extract`，状态改为 `extract`。16 线程，约 2000 条 flush 一次。抽取失败会重试并丢弃无效缓存，不把半成品标成完成。

**6. 超图构建（build）**

按文档聚合全部已抽取块。不再新建超边：把头块实体集合写回已有 `hyperedge.extra`，并绑定头块 id。正文块上的每个实体落一条 `node`，携带 `doc_id` / `chunk_id`，`embedding_content` 为「名称 + 描述」拼接文本，供后续向量检索。当前不构建 pairwise `edge`。写完后块状态改为 `build`。构图是结构化物化，不再调用 LLM。

**7. 向量索引（vectorization）**

默认对 `chunk` 与 `node` 两张表做嵌入。模型为 `Qwen3-Embedding-8B`，输出 768 维；FAISS 使用 HNSW（M=32，efConstruction=256，efSearch=128），标量量化 fp16。索引按最多 10 万向量分片，峰值内存约等于一片。SQLite 的 `embedding_status=done` 只在对应分片成功落盘后标记，中断后未落盘的行会重试（可命中嵌入缓存）。检索期删除不立刻改写 HNSW 图，只打墓碑；物理压缩需手动触发。

**8. 关键词全文索引（FTS5）**

在向量索引之外，将块正文做 Unicode `casefold()` 后写入虚拟表 `chunk_fts`（trigram 分词），以支持牌号、CAS、字段名等精确子串匹配。查询时词长不少于 3 的走 `MATCH`，短词走 `instr`。chunk 插入 / 按 id 删除会同步维护 FTS；行数与 `chunk` 表不一致时全量重建。该索引在首次检索前校验，不阻塞构建主链。

## 五、当前检索方案

在线问答默认走 **Agent**（`qwen3.6-27b`，最多 12 步）。单跳问题一次检索、一次作答；多跳再按中间结论继续检索。检索层是三路召回的并集，关键词路只增加候选、不删减向量命中。

**查询侧。** 查询改写当前关闭。查询向量会加上 Qwen3 Embedding 的 instruct 前缀（文档侧存储不加该前缀），以对齐嵌入模型的检索用法。

**向量双路。** 查询向量分别在 chunk 索引与 node 索引上做 HNSW 检索，各取 30 条；node 命中映射回所属 chunk。距离转为分数后，同一 chunk 取较高分。

**关键词路。** LLM 从问题中抽取少数值（minority：牌号、CAS、货号等可锁定文档的具体取值）与多数值（majority：如「相对密度」「NFPA」等字段键，不抽连续数值）。在预计算的小写正文上用 FTS5 `MATCH` 做包含匹配；少数值命中块数达到 `keyword_candidate_k=30` 则不再查多数值。命中按「少数值优先、再多数值个数」排序后截 30 块，再做文档级首轮 rerank，只保留 5 篇——截断仅作用于关键词路。

**合并、扩展与终排。** 三路按 chunk 并集，`score` 取 max，`match_type` 可叠加。命中文档在 `enable_full_body_context=true` 下写入该文全部 body；页切片文档在文首补超边头块。最后用 `Qwen3-Reranker-0.6B` 按文档打分，保留 top-10，交给 Agent 作答。

**索引形态消融（`docs/精度消融.xlsx`）。** 在约 2k 规模、100 道有主体 1-hop 题上，比较精确 L2 与 HNSW、以及 4096 / 1024 / 768 维与 fp32 / fp16。当前线上采用表中最后一列 **HNSW + 768 维 + fp16**：

| 指标 | L2 4096 fp32 | L2 1024 fp16 | L2 768 fp16 | HNSW 4096 fp32 | HNSW 4096 fp16 | HNSW 1024 fp32 | HNSW 1024 fp16 | HNSW 768 fp32 | **HNSW 768 fp16（现用）** |
|---|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| 准确率 | 0.91 | 0.90 | 0.87 | 0.92 | 0.92 | 0.89 | 0.88 | 0.89 | **0.87** |
| 召回率 | 0.90 | 0.85 | 0.84 | 0.85 | 0.84 | 0.84 | 0.84 | 0.83 | **0.83** |
| 意外失败数 | 0 | 0 | 1 | 0 | 0 | 0 | 1 | 0 | **1** |

相对精确 L2、4096 维、fp32，现用配置在该小库 1-hop 集上准确率低 4 个百分点、召回低 7 个百分点，换来分片 HNSW 与半精度，使后续十万级节点可以常驻检索。HNSW 在 4096 维上准确率甚至略高于 L2（0.92 vs 0.91），主要损失发生在降维到 768。

**与 2k 基线评测的对比。** 基线为 `benchmark_results_2k/report_subject_4096_fp32_l2.json`（2026-08-11，对应上表第一列）；当前为 `benchmark_results/report_complex.xlsx`（2026-08-22，Agent + 768d HNSW fp16 + 关键词路 + 全文扩展）。两套题并非同一抽题：基线 seed=42、仅 1-hop 100 题；当前 seed=44、1-hop 100 + 2-hop 50 + 3-hop 50。语料规模也已从约 2k 扩到当前库。

| 指标 | 2k 基线（L2 4096 fp32） | 当前自生成集 | 变化 |
|---|---|---|---|
| 题量与结构 | 100 题，全部 1-hop | 200 题（1 / 2 / 3-hop = 100 / 50 / 50） | 增加多跳 |
| 嵌入与索引 | 4096 维、fp32、精确 L2 | 768 维、fp16、HNSW | 与消融现用列一致 |
| 总体正确率 | **91.0%**（91/100） | **78.5%**（157/200） | 含多跳后下降 |
| 其中 1-hop 正确率 | 91.0% | **80.0%**（80/100） | −11 pp |
| 文档召回 | **90.0%** | 总体 62.9%；1-hop **73.0%** | 1-hop −17 pp |
| gold 全中且答对 / 全中且答错 | 87 / 3 | 97 / 0（200 题口径） | 当前全中则几乎全对 |
| 平均检索耗时 | 14.2 s | 总体 14.8 s；1-hop **11.7 s** | 1-hop 检索略降 |
| 平均作答耗时 | 39.4 s | 总体 77.7 s；1-hop **64.2 s** | 上下文扩全文、回答变长 |
| 纯 LLM 对照 | 未测 | 正确率 11.5%；超图 pairwise 胜 170/200 | 当前可量化相对无检索的收益 |

1-hop 正确率从 91% 降到 80%、召回从 90% 降到 73%，不能单归因于 HNSW/768：消融里同一套 2k 题从 L2 4096 fp32 换到 HNSW 768 fp16 只掉到 87% / 83%。其余差距来自大库噪声、题集重抽（seed 变化）以及多跳题把总体召回拉到 62.9%。收益侧是索引可扩展、1-hop 检索时延略降，并补上了纯 LLM 对照（11.5% vs 超图 78.5%）。

## 八、结论

1. **在约 3.4 万份原始 PDF、4.9 万文档切片、155 万节点的当前库上，超图 RAG 已经能稳定跑完整评测。** 两套外部集严格正确率分别是 **80.2% / 77.2%**，宽松正确率都在 **98%** 左右；自生成事实题正确率 **78.5%**。
2. **相对纯 LLM 的优势主要在「完整、可核验」，而不是「完全不会」。** 外部集上宽松正确率双方接近，但超图 3 分占比高很多（74.8% / 68.6% vs 23.9% / 26.1%），pairwise 胜率约 **74% / 71%**。自生成题上纯 LLM 只有 11.5%，说明库内具体参数几乎只能靠检索。
3. **当前短板是检索，不是生成。** 自生成集上「召回全中则全对」；外部集上参数查询、问题诊断、交叉验证、质检应用类题目明显更弱。多跳文档召回从 1-hop 的 73% 掉到 3-hop 的 47%。
4. 8 月 24–26 日已把文档 summary 写入检索上下文，并把关键词匹配改为 FTS5。这些改动还没回刷两套外部集，现有评测数字对应的是 8 月 22 日前的检索配置。
