# WeKnora 与 Chemical-Graph-RAG：知识库构建与检索对比

调研日期：2026-09-22。对照对象是腾讯 WeKnora `main` 分支（README 徽章版本 **0.8.0**）与本仓库当前实现。WeKnora 的产品介绍以 [README_CN.md](https://github.com/Tencent/WeKnora/blob/main/README_CN.md) 为准；入库、分块、检索引擎、图谱和问答管线的行为以仓库内 `website-docs/` 架构文档及其引用的源码路径为准。本项目以 `src/module/`、`src/agentic/`、`src/utils/storage.py` 和 `example/a/config_open.yaml` 为准。

## 1. 结论

两边都是「解析 → 分块 → 向量索引 → 混合召回 → 重排 → 生成」，但知识单元和图谱的定义不同。

WeKnora 是通用企业知识框架。文档解析成 Markdown 后按字符切块，默认同时建稠密向量和 BM25 关键词索引，再用倒数排序融合（RRF）合并。知识图谱是可选的 Neo4j 实体—关系图，查询时做一跳邻居补召回。摘要、检索问题、Wiki 页面、图片说明都是入库后的富化，主索引在富化完成前就可以检索。

本项目是化工技术资料（TDS、专利、MSDS）的离线批处理索引。PDF 先整段识别成中文纯文本，再为每份文档写一段「产品名片」摘要，摘要单独成头块，正文按 token 切块。图谱不建关系边：每个实体是挂在块上的节点，节点文本单独向量化，检索时和正文块、牌号/CAS 精确匹配三路并集。回答阶段再按文档把命中扩成更完整的正文。

因此，WeKnora 强在格式覆盖、多库多租户、关键词与向量的通用融合，以及可开关的关系图谱。本项目强在扫描件化工资料的保真转写、牌号和 CAS 这类稀有标识的精确命中，以及「一篇文档 = 一条摘要超边 + 一批实体节点」的领域结构。

## 3. 知识库是怎么建出来的

### 3.1 入口

WeKnora 的入库是异步管道。上传文件、导入 URL 或手工录入只负责落库和入队，解析、分块、嵌入和富化由 Worker 消费。文件按扩展名白名单进入（PDF、Word、Markdown、HTML、EPUB、图片、表格、PPT、音视频转写等）。同一租户、同一库内用 MD5、文件名、类型和大小去重。处理配置可以按知识库默认，也可以按这一次上传覆盖解析引擎、分块、多模态、图谱和问题生成。文档状态从 `pending` 到 `processing`，索引写完即可检索（`enabled`），摘要、问题、图谱、Wiki 在 `finalizing` 里收尾。失败有重试，后台约每 5 分钟扫一次卡死任务。

本项目的入口是本地目录里的 PDF（以及少量图片）。`download_from_oss()` 可以从业务库把对象拉到 `working_path/doc`，识别和插入要另跑。`main.py` 当前顺序是 `summary → chunk → extract → build → vectorization`，识别插入在更早的 `insert` 阶段。阶段之间用 SQLite 行状态衔接（`new` / `extract` / `build`，向量用 `embedding_status`）。没有按文档的任务队列，也没有「索引完成即可检索、富化以后再补」的拆分：实体节点要等抽取和构图结束才进入向量化。

### 3.2 解析

WeKnora 把解析和理解拆开。Python docreader（或 Go 进程内的 anydoc）负责把文件变成 **Markdown + 图片字节**。PDF 逐页判断是文本页还是扫描页：文本页走文本层，必要时做栏序重建；扫描页渲染成 JPEG，OCR 交给后面的多模态任务，而不是在解析器里做。图片、表格、网页、EPUB、思维导图等各有解析器。可选引擎还包括 MarkItDown、OpenDataLoader、MinerU、PaddleOCR-VL。解析器不做 VLM。嵌入图和扫描页之后才做 OCR 或图像说明，并单独建成可检索的子块。

本项目把解析和理解合成一步。`Doc.recognize_pdf` 有两条后端，配置二选一：

- 视觉语言模型：按页渲染成图，一次看完这一段的页面，按化工资料提示词输出中文纯文本。数值、单位、CAS、范围端点要求原样保留，表格改写成完整句子。
- PaddleOCR-VL：版面识别得到 HTML/Markdown，再收成纯文本。

这一步是两边成本结构差最大的地方。WeKnora 对可选文本的 PDF 几乎不调用大模型；本项目默认每段都调用视觉模型，换来的是扫描件、中英混排表格和临界数值的统一中文正文。

### 3.3 分块

WeKnora 在 Go 侧分块，默认目标大约 **512 字符、重叠 80 字符**。`auto` 会先给文档画像，再在三档里回退：Markdown 标题切分、版面启发式（分页、章节号、中英德章节标记）、递归分隔符切分。标题切分会在嵌入时给块加上「一级标题 > 二级标题」面包屑。父子分块打开后，小的子块进向量索引，大的父块只留在数据库里，命中子块后再把父块内容送进模型。短文本块还会向前后邻居补到大约 850 字符。表格分块会把表头带到从中间切开的块上。块可以在界面里改，改完重建这一块的索引，并保留版本。

本项目在摘要之后分块，单位是 **token**（`cl100k_base`），`chunk_size_max: 512`，`chunk_overlap: 0.1`。规则是：

- 该文档的摘要整段写入一条头块（`name=head`），不再切开。
- 识别正文按句号、问号、叹号和换行切句，打包到 512 token；超长句再按 token 滑窗。
- 重叠尽量按整句保留，退化为字符后缀，避免把英文单词粘在一起。

没有标题感知、父子块、表格表头回贴，也没有块级编辑和版本。头块承担的角色接近 WeKnora 的「文档摘要 + 父块上下文」，但是它本身也进向量索引，并且在直接检索里还会触发整篇正文扩展。

### 3.4 摘要、问题和图片

WeKnora 的后处理是四类独立任务，和主索引解耦：

| 富化     | 粒度            | 作用                                                                        |
| -------- | --------------- | --------------------------------------------------------------------------- |
| 文档摘要 | 每篇 1 次       | 文档级摘要，有独立状态；分块被改后会刷新                                    |
| 检索问题 | 每 20 个块一批  | 写到块的元数据，重排时拼进待重排文本                                        |
| 图谱抽取 | 每个文本块 1 次 | 见下节                                                                      |
| Wiki     | 按库批量        | Agent 生成互相链接的 Markdown 页，这些页自己也可被检索，重排后有 1.3 倍加权 |

图片说明和 OCR 各成为一个子块并进入向量索引，搜图片描述可以回到所在正文块。FAQ 库不走这套分块，一条标准问答就是一个检索单元，还可以配置「不要用这条回答的问题」。

本项目的摘要是构建主路径的一环，不是可跳过的富化。`Summary` 读识别正文，按 `doc_summary` / 化工产品名片提示词写出：品名、型号、CAS、关键规格、用途、安全和供应商。每篇文档一条 `hyperedge`，内容就是这段摘要。长 PDF 后段可以带上前一段识别正文再总结（`enable_prior_context`，当前配置为关）。没有「为每个块生成检索问题」，也没有跨文档 Wiki。图片信息已经折进识别正文，没有单独的图片向量。

### 3.5 图谱：关系图和超边节点

这是两边最容易被名字带偏的地方。两边都叫图谱，存的东西不一样。

**WeKnora** 要同时打开环境变量 `NEO4J_ENABLE` 和该库的抽取配置。每个文本块调用一次对话模型（文档给出的抽样参数是 temperature 0.3、关闭 thinking），抽出实体（名称、属性）和关系（起点、类型、终点）。写入 Neo4j 时按知识库和文档打标签，同名实体的 `chunks` 做并集，关系用 APOC 幂等合并。抽取提示可以加领域 few-shot 和关系类型标签。查询侧从用户问题里再抽实体名，用 `name CONTAINS` 做一跳邻居，把邻居节点带的、向量检索还没命中的 chunk 补进候选。Agent 另有 `query_knowledge_graph` 工具。没开 Neo4j 时这些步骤是空操作。仓库里还有一套内存版图构建（PMI 和强度打关系权重、输出 Mermaid），文档写明它当前没有接到启动装配上，在线抽取走的是异步任务和 Neo4j。

**本项目** 的 `Build` 明确不新建关系边。`edge` 表在库结构里还在，构图不写它。实际结构是：

- 一条超边 = 一篇文档的摘要（`hyperedge.content`），构图阶段只把头块上的实体写进超边的 `extra`。
- 一个节点 = 块上抽出的一个实体。`extract_product` 要求输出 `实体名 → 中文描述`，重点是品名、型号、成分、规格、用途、包装储存、生产商、CAS 等编号。描述里要出现完整名称。
- 节点的嵌入文本是「实体名 + 换行 + 描述」。节点记下 `chunk_id`、`doc_id`、`hyperedge_id`。
- 同名实体不去重、不合并跨文档节点。邻居查询是 SQL：先按名字、节点 id 或文档 id 找到种子，再取同一超边或同一文档上的其他实体。这是共现，不是「生产商—产品」「不相容物质」这种带类型的边。

WeKnora 的图回答的是「这两个东西在文档里是什么关系，关系落在哪些段落」。本项目的节点回答的是「这个牌号 / CAS / 规格在哪一块里被写成了一个可向量检索的实体」。化工资料里大量问题是标识符和指标，节点向量补的是正文向量对短实体不敏感的那一块；它补不上 WeKnora 那种沿关系走一跳的召回。

### 3.6 索引和存储

WeKnora 的向量和关键词写在同一套检索引擎里，引擎可替换：默认 PostgreSQL（pgvector halfvec + HNSW，ParadeDB BM25），另有 SQLite、Elasticsearch、OpenSearch、Qdrant、Milvus、Weaviate、Doris、腾讯云 VectorDB。混合检索始终在应用层做，引擎只需要分别提供向量和关键词。不同库可以用不同嵌入模型和不同向量库实例；一次多库查询要求嵌入模型身份一致。块可以单独停用，停用必须同步到索引。知识库创建后不能改绑定的向量库，换引擎要重建索引。

本项目是单机两套存储：

- SQLite `main.db`：`doc`、`chunk`、`hyperedge`、`node`、`edge`。`chunk` 上有 FTS5，分词器是 **trigram**，索引的是正文的小写形式；短于 3 个字符的词 FTS 覆盖不到，改走 `instr`。
- FAISS：按表分片，当前配置 `shard_max_vectors: 100000`，HNSW（M=32，efConstruction=256，efSearch=128），向量 `fp16`，维度 768。向量化默认只做 `chunk` 和 `node`。文档表和超边表有向量接口，默认不建。
- 检索可以只打开 id 区间重叠的分片，并可以把这些分片钉在内存里。开发配置的窗口注释把 TDS、专利、MSDS 分成前后相接的 id 段。

嵌入模型固定为 Qwen3-Embedding-8B，请求里带 `dimensions: 768`，要求服务端做降维并归一化。块的向量来自块正文（头块就是摘要），节点的向量来自「名字 + 描述」。

规模上，WeKnora 的设计目标是多租户、多库、可水平加向量库。本项目把百万级节点和十万级块收在一个进程的 FAISS 分片里，换取的是化工库上的可控延迟，代价是内存（全量钉住时节点索引大约数 GB 到十余 GB）和单机上限。

## 4. 检索是怎么做的

### 4.1 查询理解

WeKnora 的快速问答先走 `QUERY_UNDERSTAND`：用对话模型把问题和历史改写成 JSON，同时给出意图（查库、闲聊、追问、总结、要澄清等）。只有需要查库的意图才进入检索。图谱打开时，同一步再从问题里抽实体名。召回偏少时还有一轮不调用模型的查询扩展（去停用词、调词序、抽短语；中文用 jieba），关键词阈值放宽、TopK 放大。

本项目的改写器存在（`query_rewrite`，要求保住 CAS、型号和连字符）。查询向量前缀：只给查询加一句 Qwen3 的检索指令，文档侧不加。关键词不是 BM25 查询本身，而是另一次模型调用，从问句里抽出「少数词」（牌号、CAS、货号）。

### 4.2 召回

WeKnora 的 `HybridSearch` 是所有入口（快速问答、Agent、搜索 API）的汇合点：

1. 按向量库实例分组，多组并发，每组有超时。
2. 文档库同时做向量检索和关键词检索；FAQ 库只做向量。
3. 过召回大约是 `TopK × 5`，池子有上限（文档写的是 500）。
4. 两路都有结果时用加权 RRF：`向量权重 / (k + 向量名次) + 关键词权重 / (k + 关键词名次)`。关键词分不做归一化，因为 RRF 只用名次。
5. 图谱一路与上面并行。实体在 Neo4j 里一跳展开，新的 chunk 并入候选，按 chunk id 和内容签名去重。

本项目的 `Retrieve` 是三路，然后按块取并集（只加不删，分数取最大，不用 RRF）：

| 路           | 当前配置                  | 做法                                                                                                                                |
| ------------ | ------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| 正文块向量   | `chunk_candidate_k: 40` | 查询向量对 chunk 索引                                                                                                               |
| 实体节点向量 | `node_candidate_k: 40`  | 查询向量对 node 索引，再映回所属块                                                                                                  |
| 标识精确匹配 | 开，只要少数词            | 模型抽出 CAS / 牌号等，FTS5 trigram 或短词`instr`；少数词已经够候选就不再查多数词；再做一次文档级重排，截到 `keyword_top_k: 10` |

关键词路可以和向量路并行（`enable_parallel_paths`，当前为关）。id 窗口同时限制向量检索和关键词扫描。agentic 的 `search` 把三路收成 `hybrid` / `keyword` / `node` / `chunk` 四种模式，候选数更小（各 20，重排后 10 条）。

差别在关键词的假设。WeKnora 假设查询和正文共享词项，用分词器 + BM25 排序，适合自然语言问句对通用文档。本项目假设化工问句里真正要精确命中的是稀有字符串（CAS、货号、牌号），用模型先把它们拣出来再做子串匹配，避免「乳液」「树脂」这类高频词把 FTS 打满。`keyword_max_df: 2000` 会丢掉命中块数过多的词。多数词一路默认关闭，就是这条取舍。

### 4.3 重排和送进模型的上下文

WeKnora 重排前会清掉 Markdown 语法噪声（围栏、表分隔线、链接标记），再把图片说明、OCR 和生成的检索问题拼进待重排文本。重排分和检索分、来源权重合成 `0.6 / 0.3 / 0.1`。FAQ 可以加权；Wiki 页再乘 1.3。然后用 MMR（相关性 0.7、与已选结果的 Jaccard 冗余 0.3）做多样性。合并阶段把同一文档里相邻块拼起来，子块换成父块内容，过短的块向前后邻居补字，和历史引用做一次有限回灌。无结果可以走固定兜底或让模型不查库直接答。引用在流式输出前先推给前端。

本项目的终轮是文档级重排（Qwen3-Reranker-0.6B），`rerank_top_k: 20`。重排之后做文档扩展，由两个开关决定送进模型的正文有多长：

- `enable_full_body_context: true`（直接检索的当前配置）：命中文档的全部正文块都进入上下文；被切开的长 PDF 在文首补上头块。
- `simple`：不补未命中的正文，只在命中过正文时把头块放在最前。
- `enable_slice_family_expand`：命中任一段就把同一源 PDF 的各段按顺序接上。当前关闭。

agentic 的检索把全文扩展关掉，工具只回预览和 `doc_id` / `chunk_id` / 前后块 / 同源其他段。模型再用 `read_doc` 读一整段，或用 `read_chunk` 核对一个数。证据槽把已经核对过的字段（主体、字段、值、单位、来源 id）留下来，旧工具原文被压缩后仍以证据槽为准。

WeKnora 用父子块和邻居扩展控制上下文长度，本项目的直接检索用「整篇正文」换完整性。对几页的 TDS 这很合适；对长专利，agentic 改成「先窄召回、再按段阅读」就是在避开这份成本。

### 4.4 Agent 能调用什么

WeKnora 的快速问答不进 Agent 循环，就是上面这条插件管线。智能推理是 ReAct，工具按智能体配置裁剪。和知识相关的核心工具是 `search_knowledge`（混合检索）、`read_document`（按序把块拼回正文）、`query_knowledge_graph`（仅当范围内有启用图谱的库）、Wiki 读写，以及联网搜索、MCP、技能沙箱。预设里有纯 RAG、Wiki、混合、表格分析（DuckDB）。图谱工具在没有图谱库时会从白名单拿掉，避免模型反复调用一个空工具。

本项目有两套问答：`src/agent` 是有步数上限的计划—执行图；当前线上主路径是 `src/agentic` 的工具循环（最多 32 轮，接近上下文上限就强制收束）。工具只有五个，全部对着这一套化工库：

| 工具                | 作用                                          |
| ------------------- | --------------------------------------------- |
| `search`          | 完整问句，模式为混合 / 关键词 / 节点 / 正文块 |
| `read_doc`        | 按`doc_id` 读这一段的全部块                 |
| `read_chunk`      | 按`chunk_id` 核对一块，或跳到长 PDF 的邻段  |
| `graph_neighbors` | 同一超边或同一文档上的其他实体                |
| `note_evidence`   | 把核对过的字段写入证据槽                      |

没有联网、MCP、技能沙箱，也没有跨库扇出。`graph_neighbors` 返回的是共现实体名单和预览，不返回关系类型。

## 5. 对照总表

| 环节     | WeKnora                                   | 本项目                                                |
| -------- | ----------------------------------------- | ----------------------------------------------------- |
| 解析产物 | Markdown + 图片                           | 化工向中文纯文本                                      |
| 扫描件   | 渲染后单独 OCR                            | 视觉模型或 PaddleOCR-VL，与正文同一条流水线           |
| 分块     | 字符；标题 / 启发式 / 递归；可父子块      | token 512、重叠约 10%；摘要头块 + 正文块              |
| 摘要     | 可选，不挡住检索                          | 必经，且作为头块参与检索                              |
| 检索问题 | 每批块生成，重排时使用                    | 无                                                    |
| 图谱     | Neo4j 实体和带类型的关系，一跳补召回      | 文档超边 + 实体节点；不建关系边；节点向量是一条召回路 |

## 6. 对化工库有用的差异

下面只写和现有流水线直接相关的差异，不把 WeKnora 的平台功能（IM、多租户、沙箱）算进来。

**标识符召回应该继续走现在这条路。** CAS、货号、牌号用 BM25 或普通分词容易被切开或被高频词淹没。先抽出少数词再做 trigram / 子串，比 WeKnora 的默认关键词引擎更贴这批语料。RRF 解决的是「向量名次和关键词名次不可比」，本项目用并集加分数取最大，再交给交叉编码器，标识符命中不会因为向量分更高而被融掉。

**关系边是 WeKnora 有、这里故意没建的能力。** 现在的邻居是「同一篇资料里还提到了谁」。问「这家公司还有哪些产品」「这个物质和哪种体系不相容」时，共现能给出候选，但不能说明边的类型，也不能跨文档把同名实体收成一个点。若要补，更接近 WeKnora 的做法是：抽取时增加关系类型，同名实体在写入时合并 `chunk_id` 列表，查询时沿边取还没被向量命中的块。这会把现在「每块一次抽取、只产出名字和描述」的成本再抬一截，抽取提示也要从 `extract_product` 扩成带关系的 JSON。

**标题面包屑和检索问题，取决于识别正文的结构。** WeKnora 的标题切分要求 Markdown 标题。本项目的识别结果是按阅读顺序写的纯文本，标题树不稳定，直接套 heading 策略收益有限。更接近现有数据的是：头块（产品名片）已经在扮演文档级上下文；若召回经常差在「问法与正文用词不一致」，WeKnora 那种按块生成检索问题、并在重排时拼进去，比再改分块策略更对症。

**入库形态不同，不适合照搬队列来换能力。** WeKnora 单文档入队、索引先可用、富化后补，适合持续上传。本项目一次处理上万篇扫描件，阶段化批处理和嵌入缓存是为这个批量服务的。
